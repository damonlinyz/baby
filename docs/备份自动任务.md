# 加密备份、定时任务与恢复检查

`backend/backup_jobs.py` 在原有 `maintenance.py` 之上增加独立运维命令。需要 Linux、Python 3.9+、IANA 时区数据和支持 CMS AES-256-GCM 的 OpenSSL 3。本地备份命令不依赖 Python 第三方库，不调用网络或消息服务。可选异地同步与 Webhook 另见 [异地备份与发布工具](异地备份与发布工具.md)。

本轮交付为可运行的本地工具、systemd 模板和合成恢复测试。**尚未在生产主机启用定时器，也未配置异地存储或通知接收人。** 下面安装命令供实际部署时执行，不代表这些服务已经运行。

## 准备恢复密钥

在独立、可信的恢复电脑生成专用 RSA 证书和加密私钥，交互式设置私钥口令：

```sh
umask 077
openssl req -x509 -newkey rsa:3072 -sha256 -days 3650 \
  -subj '/CN=Baba backup recovery/' \
  -addext 'keyUsage=critical,keyEncipherment' \
  -keyout recovery-private.pem -out recipient.pem
```

只将公钥证书 `recipient.pem` 放到备份主机；恢复私钥和口令在独立位置保管，并做好恢复演练。备份主机无需持有恢复私钥。证书是专用公钥载体，工具检查证书可读、未过期以及加密操作成功；没有配置外部 CA 信任链或备份签名。

加密使用 OpenSSL CMS AuthEnvelopedData 与 AES-256-GCM。外层 SHA-256 用于发现文件损坏；解密还需通过 GCM 校验、加密内外清单一致性、数据库 SHA-256、SQLite 完整性/外键与实例检查。公钥加密不证明备份的发送者身份，备份目录及异地存储仍需访问控制。

## 手动运行与保留周期

先启动一次新版应用，确保业务数据库与独立删除记录都已初始化。以下命令在仓库根目录执行，路径按实际部署修改：

```sh
python3 backend/backup_jobs.py run \
  --db private/baba.sqlite3 --directory backups/encrypted \
  --recipient-cert /etc/baba-backup/recipient.pem --kind full --keep 14

python3 backend/backup_jobs.py run \
  --db private/baba.sqlite3 --directory backups/encrypted \
  --recipient-cert /etc/baba-backup/recipient.pem --kind ledger --keep 192
```

- `full` 先快照业务数据库，再快照同实例的累计删除记录，随后检查、打包并加密。两份文件不是同一时刻的快照；后取得的删除事实会在恢复时重放。
- `ledger` 只快照累计删除记录，便于更高频备份和独立保管；它不能单独恢复业务数据。
- `--keep` 为每种类型保留的成功批次数，至少 1。每日一次完整备份时，14 批约为两周；每 15 分钟一次删除记录备份时，192 批约为两天。缺失执行会改变实际覆盖时长。
- 每个删除记录快照均包含此前全部墓碑，删除旧快照不会从当前记录或新快照中清除墓碑。
- 新批次校验并发布后才清理旧批次。只删除同实例、同类型、目录名与清单匹配、密文校验通过且仅包含预期文件的旧批次。陌生文件、损坏批次及符号链接不会自动清理。

目录首次创建为 `0700`，文件为 `0600`。已有目录必须限制其他用户访问；工具拒绝绑定另一个数据库实例，也不会覆盖已有批次。不同类型任务共用非阻塞文件锁，避免并发清理；重叠执行返回失败，保留原任务状态，下一次定时执行可再尝试。

目录结构：

```text
backups/encrypted/
  instance.json
  full.status.json
  ledger.status.json
  .backup.lock
  full/<UTC时间-随机批次号>/manifest.json
  full/<UTC时间-随机批次号>/payload.cms
  ledger/<UTC时间-随机批次号>/manifest.json
  ledger/<UTC时间-随机批次号>/payload.cms
```

清单仅含实例、时间、类型、证书指纹和文件校验信息；不包含家庭称呼或健康原文。创建备份时仍需私有明文临时文件，正常退出会清理；直接运行 CLI 被强制杀死时，临时文件可能留在系统临时目录，需由运维检查。下面 systemd 模板使用 `PrivateTmp=true`，由服务管理器在进程退出后清理私有临时目录。

## 失败与过期检查

```sh
python3 backend/backup_jobs.py status \
  --db private/baba.sqlite3 --directory backups/encrypted --kind full --max-age-hours 26

python3 backend/backup_jobs.py status \
  --db private/baba.sqlite3 --directory backups/encrypted --kind ledger --max-age-hours 1
```

成功退出码为 0，失败为 1，并输出 JSON。以下情况会失败：没有成功备份、最近任务失败、成功记录过期、系统时间异常、密文丢失/损坏、清单不匹配或实例不一致。正在运行的新任务在默认 30 分钟内可使用仍有效的上次成功记录；超过 `--max-run-minutes` 后视为超时或中断。

检查只验证本地批次和任务状态，不解密、不证明私钥仍可用，也不证明异地副本已存在。应另外定期在恢复电脑执行解密和删除重放演练。失败或磁盘故障不会将旧的成功状态伪装成新成功；恢复执行成功后状态才重新转绿。

## systemd 安装模板

`deploy/systemd/` 提供三项定时器：

| 模板 | 默认安排 | 用途 |
|---|---|---|
| `baba-backup-full.timer` | 上海时间每天 03:07，随机延迟最多 60 秒 | 完整备份，保留 14 批 |
| `baba-backup-ledger.timer` | 每 15 分钟，随机延迟最多 60 秒 | 独立删除记录，保留 192 批 |
| `baba-backup-check.timer` | 启动后约 5 分钟，此后每 5 分钟 | 完整备份 26 小时、删除记录 1 小时过期检查 |

备份定时器使用 `Persistent=true`，主机关机错过执行时会在恢复后补一次；不是补齐关机期间的所有快照。正常删除事实的灾备窗口约为 15 分钟加随机延迟和执行耗时，失败/停机时会更长，不能称为零丢失。

模板假定应用账号已存在且为 `baba:baba`，代码位于 `/opt/baba`，应用实际数据库为 `/var/lib/baba/private/baba.sqlite3`。路径不同时，同时修改环境文件、`WorkingDirectory`、`ExecStart` 与沙箱路径。应用本身也须配置相同 `BABA_DB`；备份程序不会移动数据库。

在目标主机手动核对账号、路径、权限和公钥证书后安装：

```sh
sudo install -d -m 0700 -o baba -g baba /var/lib/baba/backups
sudo install -d -m 0755 /etc/baba-backup
sudo install -m 0644 /path/to/recipient.pem /etc/baba-backup/recipient.pem
sudo install -m 0644 deploy/systemd/common.env.example /etc/baba-backup/common.env
sudo install -m 0644 deploy/systemd/full.env.example /etc/baba-backup/full.env
sudo install -m 0644 deploy/systemd/ledger.env.example /etc/baba-backup/ledger.env
sudo install -m 0644 deploy/systemd/*.service deploy/systemd/*.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start baba-backup@full.service
sudo systemctl start baba-backup@ledger.service
sudo systemctl start baba-backup-check.service
sudo systemctl enable --now baba-backup-full.timer baba-backup-ledger.timer baba-backup-check.timer
systemctl list-timers 'baba-backup*'
journalctl -u baba-backup@full.service -u baba-backup@ledger.service -u baba-backup-check.service
```

备份进程仅允许写入备份目录和私有临时目录；不能写业务数据库。单次任务运行上限 20 分钟。检查服务顺序执行两项检查，任一失败便进入 systemd 失败状态。退出码、JSON 与 journal 可接入已有监控；模板未配置邮件、微信、Webhook 等通知，也没有向任何人发送消息。

## 解密与删除重放

在可信恢复电脑创建权限为 `0700` 的父目录。私钥受口令保护时，使用环境变量名选择口令，避免将口令值写入命令历史或参数：

```sh
read -rs BABA_RECOVERY_PASSWORD
export BABA_RECOVERY_PASSWORD
python3 backend/backup_jobs.py unpack \
  --bundle /safe-backups/full/20261028T000000Z-012345abcdef \
  --private-key /safe-keys/recovery-private.pem \
  --passphrase-env BABA_RECOVERY_PASSWORD --output /safe-recovery/full
python3 backend/backup_jobs.py unpack \
  --bundle /safe-backups/ledger/20261028T001500Z-012345abcdef \
  --private-key /safe-keys/recovery-private.pem \
  --passphrase-env BABA_RECOVERY_PASSWORD --output /safe-recovery/latest-ledger
unset BABA_RECOVERY_PASSWORD
```

批次号必须替换成实际目录。未加口令的私钥可省略 `--passphrase-env`。解密默认允许的数据库总大小为 1 GiB，较大备份可显式增大 `--max-bytes`。目标目录须不存在；归档只接受固定名称的普通文件，拒绝绝对路径、路径穿越、链接、重名或缺失条目。全部检查完成后才发布到新目录，不自动替换应用数据。

**完整快照内附的删除记录只代表当时状态，不应当自动选作恢复依据。** 停止源应用及其他写入进程；只要当前最新的同实例删除记录尚在，就优先使用它：

```sh
python3 backend/maintenance.py restore \
  --backup /safe-recovery/full/database.sqlite3 \
  --ledger /current-private/baba.sqlite3.deletions.sqlite3 \
  --output /safe-recovery/restored.sqlite3
```

若原主机和最新记录都已丢失，须另行核对最新灾备删除记录的来源、时间和未同步的删除事实；工具无法补出最后一次副本之后的删除。确认依据后才可将上面 `--ledger` 改为独立解密的 `/safe-recovery/latest-ledger/deletions.sqlite3`。详细恢复后的会话、授权、邀请与订单核验步骤见 [备份与恢复](备份与恢复.md)。

## 异地保存与当前验收边界

完整业务备份和高频删除记录应有独立的异地持久化策略；本地不同子目录不等于异地灾备。可将已完成批次的 `payload.cms` 与 `manifest.json` 一起交给已配置的存储工具，复制前后核对 SHA-256。恢复时使用同一批次的两个文件。公钥可留在备份机，恢复私钥不得随备份上传。

当前未配置异地目的地、存储账号、对象保留策略或通知渠道，因此没有自动上传，没有真实故障通知送达记录，也没有证明断电后的异地恢复能力。工具使用文件与目录 fsync 尽量持久化，最终可靠性仍依赖目标文件系统、存储设备与实际恢复演练。

合成测试覆盖加密/解密、加密私钥口令、较新删除记录重放真实孕次与双胞胎资料、错误密钥和 GCM 篡改拒绝、实例冲突、锁、失败时保留旧备份、同秒批次保留、新目录不覆盖、过期/中断检查、危险归档拒绝及 CLI 非零退出。systemd 模板与日历表达式已检查；没有在本会话安装或启动服务。
